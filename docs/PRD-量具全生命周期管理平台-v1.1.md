## 0. 阅读指引与执行约定

### 0.1 文档用法

1. 不要按章节顺序开发。按 §13.1 的版本切片（S0→S1→S2）逐片交付，每片必须通过该片的验收门槛才进入下一片。
2. 凡标 shall 的规则为强制实现，删除或降级会破坏核心风险控制；标 should 的为实现建议，可因技术原因调整但须记录；标 may 的为可选。
3. 每条 FR 的验收标准是可执行用例，编码代理应将其转为自动化测试（E2E 优先）。
4. §15.5 待确认决策清单中未获用户确认的项，一律按表中默认值执行，不得停工等待；确认后若与默认值不同，按影响面回改对应章节。

### 0.2 状态词约定

| 词 | 含义 |
|---|---|
| shall（必须） | 强制实现，缺失即验收不通过 |
| should（应该） | 建议实现，不实现需在提交说明中写理由 |
| may（可以） | 可选增强 |
| must not（禁止） | 明确不允许的实现方式 |

### 0.3 平台定位

LoopForge 是赛肯的制造数字化平台，本需求为其首个业务模块 MIM（Measuring Instrument Management，量具管理）。MIM 必须独立可运行（不强依赖其他模块），并通过 org_id / plant_id 字段为后续多厂区、多模块预留扩展。

## 二、背景与目标

### 2.1 业务背景

赛肯以 ODM 方式生产渔轮（钓鱼卷线器），产品从 R&D 设计 → 制工（工艺/工装）过程验证 → QE 产品验证 推进，制造链路覆盖 模具制造 → 注塑 → 压铸 → 五金加工 → 组装。上述每个环节都依赖量具（卡尺、千分尺、三次元、投影仪、硬度计、螺纹规、块规、高度仪、粗糙度仪、百分表等）提供尺寸与形位判定依据。

渔轮是精密装配件：卷线器的齿轮啮合、轴系同轴度、壳体配合、离合间隙等，都以 0.01mm 级尺寸链为设计基础。一旦用一把超期未校或已损坏的量具做出合格判定，缺陷会以整批形式流入组装与出货，客诉后的召回成本远高于量具管理本身的投入。

因此量具管理的核心命题不是记录齐全，而是：在生产的每一刻，都能证明手上这把量具是合格的；不能证明，就不许用。

### 2.2 现状与数据证据

现有管理手段是一份 Excel 台账（《中宇公司量具管理一览表》）。对其 50 条存量记录的核查结论（原文表格）：

- 覆盖范围：仅 1 个工作表、50 条记录、6 个部门（检测中心占 80%）——无法证明覆盖全厂在用与借用中的量具。
- 台账覆盖率：现场实有约 1000–1500 台，台账仅 50 条 → 覆盖率 3%–5%——95% 以上的量具处于无记录状态。
- 台账代表性：50 条中 80% 集中在检测中心，无模具/注塑/压铸/五金/组装工序分布。
- 生命周期覆盖：只有购入/领用/上次校验/下次校验/类别/状态——申购、采购、验收、使用、维修、报废审批全部无记录。
- 已失效数据占比：报废 21 条 + 丢失 1 条 = 44%——到期预警被失效数据淹没。
- 校验结果：无合格/不合格/偏差字段——核心命题不可验证。
- 校验周期：值为文本 1年/2年/6个月，且该列被误设为日期格式。
- 使用人：无使用人字段；只有管理者，且 10 条写的是无人使用。
- 工序/位置：无工序、产线、工位、库位字段。
- 精度/允差：仅在规格自由文本中混杂（(0-25)mm、M22*1-6g、￠19.999）。
- 到期风险：非报废/非丢失的 28 件中 5 件已超期（4 件库存、1 件正常在用）。
- 空值聚类：5 条螺纹规无领用日期、无下次校验日期、管理者为无人使用。
- 审计能力：无创建人/修改人/修改时间。

结论：本平台 7 个环节中，Excel 只覆盖了登记和校验日期两个环节，且校验缺最关键的结果字段。更要紧的是——它只覆盖了全厂 3%–5% 的量具。因此本项目的主战场不是把 50 条导进去，而是把 1500 台建起来并贴上码；系统设计必须优先服务于现场清点与建码（见 M13）。

### 2.3 问题清单

| 编号 | 问题 | 现状 | 业务后果 |
|---|---|---|---|
| P-01 | 超期量具无法拦截 | 靠人看 Excel 颜色 | 超期量具照常用于判定，品质风险敞口 |
| P-02 | 校验结果与证书无归档 | 纸质/本地文件 | 客户审核、体系审核时无法举证 |
| P-03 | 使用人与工序不可追溯 | 无字段 | 出现批量不良时无法定位是哪把量具造成的 |
| P-04 | 维修后未强制复校 | 无流程 | 修好的量具直接回线，精度未知 |
| P-05 | 报废/丢失无审批留痕 | 只改一个状态字 | 实物与台账脱节，资产流失 |
| P-06 | 申购到入库链路断裂 | 无记录 | 采购周期不可控，紧急申购无依据 |
| P-07 | 提醒靠人记 | 无系统提醒 | 到期漏校 |
| P-08 | 台账覆盖率仅 3%–5% | 1500 台实机，只在册 50 台 | 系统管的是 50 台纸面资产，95% 的量具游离在管控之外 |
| P-09 | 无编号/一号多物 | 现场部分小量具无编号，或同一编号贴多台 | 实物与记录无法一一对应，扫码不可信 |

## 五、方案对比与选型

候选方案：A. Excel 增强；B. 独立轻量 Web 平台；C. 采购 EAM/MES 套件。推荐方案 B。

理由：① 只有 B 能让拦截发生在使用现场；② 渔轮 ODM 的量具管理颗粒度（编号级、工序级）需要自定义字段与状态机；③ B 可通过 PWA 在手机浏览器直接使用；④ 存量仅 50 条但现场实有 1000–1500 台，真正工作量在清点与建码。

### 5.5 技术选型（决策已定，研发按此执行）

一句话结论：单体全栈 TypeScript（Next.js）+ PostgreSQL，内网 Docker Compose 部署，移动端用 PWA，不引入微服务、不引入 Kubernetes、不做原生 App。

| 层次 | 选型 | 版本 |
|---|---|---|
| 前端 + 后端 | Next.js（App Router）+ TypeScript | 14.x LTS |
| UI | Tailwind CSS + shadcn/ui | 最新稳定 |
| 数据库 | PostgreSQL | 16 |
| ORM | Prisma | 5.x |
| 认证 | 自建会话（工号+密码，bcrypt）+ JWT/Session Cookie | — |
| 扫码 | @zxing/browser + 隐藏 input 接收扫码枪键盘流 | — |
| 二维码生成 | qrcode（服务端 PNG/SVG） | — |
| 标签打印 | pdfkit 服务端生成 A4 PDF（24 格） | — |
| 定时任务 | 应用内 node-cron（单实例）+ pg_advisory_lock | — |
| 附件存储 | 本地磁盘卷 + Nginx 直出 | — |
| 部署 | Docker Compose（app + postgres + nginx）+ 每日 pg_dump | — |
| 监控 | 应用日志（pino）+ Nginx access log | — |

明确的"不选"：Java Spring Boot + Vue（两套语言迭代慢）、微服务/K8s（运维成本大于收益）、原生 App（PWA 足够）、低代码（状态机表达退化）、SQLite/Excel 二次开发（并发与权限不成立）、MongoDB（强关系需事务约束）。

容量校核（按 1500 台）：档案 1500（+20%=1800）、使用记录 30 万条/年（5 年 150 万）、校验记录 1800/年、证书附件 360MB/年、峰值早班 8:00–8:30 约 500 次登记（原文写 5–8 QPS 均值，实际约 0.28 QPS，见评估第 7 条）、扫码判定 P95 ≤80ms。

研发约束（写进 CI）：① 关键业务规则纯函数 + 单测（calcNextDue / calcCalStatus / decideAvailability / genMgmtNo）；② 时间一律 timestamptz，服务端为准；③ 状态变更走统一 transition()，禁止页面直接 UPDATE；④ availability / cal_status 派生字段只允许重算函数写入；⑤ 类型检查 + ESLint + 单测 + 迁移可重放，四项通过才允许合入主干。
