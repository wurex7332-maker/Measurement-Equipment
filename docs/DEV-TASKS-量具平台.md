# MIM 开发任务卡（S0 可直接开工）

> 配套文档：`PRD-量具全生命周期管理平台-v1.1.md`（技术选型见其 §5.5，已决策，不要再讨论）
> 用途：给 AI 编码代理按序执行。每张卡完成 → 跑该卡"验证" → 通过才领下一张。
> 技术栈（已确定）：Next.js 14 App Router + TypeScript + Prisma + PostgreSQL 16 + Tailwind + shadcn/ui。内网 Docker Compose 部署，移动端 PWA。
> 规模基准：档案按 1500 台规划（容量 1800）；S0 的主战场不是导入 50 条，而是把 1500 台建出来贴上码。

---

## 执行纪律

1. 按卡号顺序执行，T0 未通过不得开始 T1。
2. 每张卡必须产出：代码 + 迁移脚本 + 至少 1 个自动化测试。无测试视为未完成。
3. 每张卡的"验证"是可执行命令或可复现操作，不接受"看起来对"。
4. 遇到 PRD 未定义的细节：按 PRD §15.5 默认值实现，并在 `docs/DECISIONS.md` 追加一行记录（决策 / 原因 / 影响文件）。
5. 禁止自行扩展范围。新想法写入 `docs/BACKLOG.md`，不实现。
6. 涉及状态判定、编号生成、到期计算的逻辑必须是纯函数 + 单测，不得内联在页面里。

## 编码代理注意事项

1. 核心风险点只有三处，实现时优先保证正确：到期自动置不可用（T3）、使用登记硬拦截（T5）、维修后强制复校（T12）。其余功能出 bug 是体验问题，这三处出 bug 是品质风险。
2. 第四处隐性风险：建档体验。T2b 如果做得慢（>90 秒/台），1500 台根本建不完，整个项目会停在"系统做好了但只有 50 条数据"。这一条的优先级等同前三处。
3. 所有状态变更走统一 `transition()` 服务，禁止在页面直接 `UPDATE status`。
4. `availability` 与 `cal_status` 是派生值，任何写入路径都必须通过重算函数，不允许手工赋值。
5. 时间统一用 `timestamptz`；到期判定以服务端时间为准（防客户端改时间绕过）。
6. 编号段位满 999 自动切下一段位（10→11），保持 3 位流水，不要擅自改成 4 位——存量 50 条都是 3 位，混排会让现场人员读错号。
7. 迁移脚本必须可重复执行（幂等），生产环境执行前必须先 dry-run 并留存报告。
8. 预生成但未使用的编号不得静默回收（会与已贴出的实物标签冲突），只能由管理员显式作废。
9. 列表与看板默认只查 1800 条量级，不要提前做分库分表；但使用记录表从第一天就要有 `(instrument_id, used_at)` 与 `(work_order_no)` 两个索引。
